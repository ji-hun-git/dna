## PR 7a — parser honesty, value contract, idempotency/concurrency/state, hand-labelled fixtures

Branch `codex/wave13-backend-hardening` (HEAD `a30db43`, stacked on `codex/wave11-alive-home`). Tasks 1–13 (spec §2, §3, §4, §9). Synthetic only. Release remains NO_GO; no readiness gate or verdict changed by this PR. Gates were run on 2026-09-19.

### What 7a built

- **Worker — no silent drop (§2).** `NativeTextExtractionProvider.parseRow` never returns `null`: a labelled numeric row either becomes a candidate or one of exactly seven closed abstention reasons (`unreadable`, `ambiguous_value`, `ambiguous_unit`, `missing_evidence`, `qualified_value`, `qualitative`, `previous_column`); a row with no label before its first numeric token (page numbers, institution lines) is `RowParse.Skipped`, not an abstention. Row grammar: value-before-label, glued units (`5.6%`, `188mg/dL`), `<`/`≤`/`>` qualified values → `qualified_value` (the printed comparison is never stored as a number), qualitative results (음성/양성/정상/이상) → `qualitative`. `혈압 120/80 mmHg` splits into two candidates labelled `혈압(수축기)`/`혈압(이완기)` (resolving to `systolic-blood-pressure`/`diastolic-blood-pressure` via two new catalogue aliases), with the printed label `혈압` carried on both as `originalLabel` end to end (candidate → confirmed record → health event → export). **(Review Fix F1)** A blood-pressure row followed by a *second*, unheadered pressure pair (`혈압 118/76 mmHg 121/79 mmHg`) no longer silently drops the second pair: headerless, the whole row now abstains `ambiguous_value` honestly; under a real previous-result header, the this-time pair still becomes two candidates and the previous-time pair now correctly abstains as two `previous_column` rows (`혈압(수축기)`/`혈압(이완기)`) instead of the pair vanishing. **(Review Fix F2)** A value-first row whose leading token is qualified (`<0.3 mg/L hs-CRP`), otherwise numeric-like-but-not-plain (`120/80 mmHg 혈압`), or a plain value followed by an unrecognized unit but a real label further down the row, no longer silently `Skipped`s when a label is present: it now abstains `qualified_value`/`ambiguous_value`/`ambiguous_unit` respectively. **(Review Fix F3)** The 100-candidate/100-abstention caps no longer truncate silently past them: one `UNREADABLE` abstention labelled `결과지` is emitted once for any overflow, itself kept inside the abstention cap.
- **Worker — positional columns and dates.** `PositionalLineGrouper` reconstructs same-baseline multi-column rows by x-gap token grouping instead of raw `PDFTextStripper` order; a previous-result column is only recognized when a real header (이전/전회/직전 or a year) sits above it (`previous_column`) — a headerless duplicate value in a second column stays the honest `ambiguous_value`, not a silently-accepted second candidate. Labels that continue onto a following line are joined before parsing. Date rules: Korean compounds (재검사일 등) excluded by lookaround, English `report`/`print`/`printed`/`issue`/`issued`/`reported`/`generated`/`received` prefixes excluded from the exam-date label, `검사일자` now covered, two-digit years remain unsupported (stated, not silently wrong). `joinValueColumns`' column-grouping now recognizes a pressure-pair-shaped cell (`121/79`) as starting its own value group (Fix F1), so a this-time/previous-time pair of pressure cells stays two groups instead of the second silently folding into the first.
- **Core — value contract (§3, founder decision 1).** `CandidateConfirmationRequest.value` and `RecordCorrectionRequest.value` now accept the worker's own grammar (`^-?(\d{1,3}(,\d{3})+|\d+)(\.\d+)?$`, `@Size(max = 64)`) and store it verbatim (commas kept); all arithmetic still goes through `ChangeDeltaCalculator.parse` (commas stripped). Integration-proven: `250,000 /µL` confirms, `-2 mmol/L` confirms, `1.234 µIU/mL` corrects, a 65-character value → `400 request_invalid`.
- **Core — idempotency, concurrency, state (§4).** V13 adds `request_sha256` and `expires_at` (24h) to `gc_idempotency`; the same key against a different resource or request hash → `422 idempotency_key_mismatch`; an expired key is treated as new. Every confirm/exclude/correct/document-request path takes `SELECT … FOR UPDATE` on the target row before its state check (`check(it == 1)` sites removed); a state that changed under a competing request ends in an explicit `409 candidate_state_changed`/`record_state_changed`, proven by two real two-thread races through `FoundationLifecycleService` against the embedded PostgreSQL (`CountDownLatch`-started, never mocked) — contract change: a fresh confirmation key racing against an already-`CONFIRMED` candidate now returns `409`, not a second success. Framework exceptions (bad JSON, missing header, non-UUID, lock conflict, plus the two newly-mapped `ConstraintViolationException`/`MaxUploadSizeExceededException`) answer the existing `problem+json` shape with `Cache-Control: no-store` and never echo the request body; a log-capture test proves a 500/503 is observed through `PhiSafeLogger` with only the exception's simple class name, never a value or message. `V13` also adds the `TERMINATED_BY_REVOCATION` document status and an append-only trigger on `gc_audit_event`.
- **Core — same-day rule, ordering, sticky CORRECTED.** `/changes` and `/series` share one same-day rule (`SameDayRule.hasDefinedOrder`); records, health events and exports all sort `observedOn, confirmedAt, recordId` (label dropped from the tie-break, including the FHIR bundle mapper). `reviewDecision` stays `CORRECTED` once a record has any correction history even if a later correction reverts the value and date to the original; the web now says `수정 이력이 있지만 지금 값은 원래 값과 같아요` instead of falsely claiming a difference. **(Review Fix F4)** All five read models now truly order on the same immutable instant: `FoundationRecordRow` gained `confirmedAt` (mapped from `r.confirmed_at`, distinct from the pre-existing mutable `versionChangedAt` which a correction still bumps), and `HealthEventProjection`/`FhirExport`/`SeriesProjection`/`ChangeSummaryProjection` — which previously ordered on the mutable `versionChangedAt` while `/records` alone used the immutable `confirmed_at` — now all order on `confirmedAt` too. A correction can still shuffle same-day ties (nothing here changes which record is "same day") but can no longer reorder any of these five read models relative to one another or relative to `/records`. The HTTP `confirmedAt` field on a health event is unchanged in meaning: it still carries the mutable `versionChangedAt`, exactly as before.
- **Core — revocation and deletion (founder decision 2).** Revoking `DOCUMENT_EXTRACTION` moves every document of that consent that is in `REVIEW_REQUIRED`, `UPLOAD_PENDING`, `UNTRUSTED_OBJECT`, `SECURITY_INSPECTION`, `SECURITY_APPROVED`, `EXTRACTION_QUEUED`, `EXTRACTION_RUNNING` or `FAILED_RETRYABLE` to the new terminal `TERMINATED_BY_REVOCATION` status and deletes its quarantine files (untrusted/approved/preview) after commit; `FoundationDocumentStorage.deleteAll` continues past a failing key (logs the failure through `PhiSafeLogger`, never the filename) instead of abandoning the rest of the batch, and a preview row survives a failed file delete so the (7b) janitor can still find and sweep the orphan. Deletion commits the row deletions first, deletes files after commit, and additionally purges `gc_idempotency`, `gc_session` and `gc_upload_capability` rows for the subject. **(Review Fix F5)** `terminateDocumentsForRevokedConsent` previously locked `gc_document` then `gc_document_job`, the opposite order from every worker completion path (`lockLeasedJob`'s `FOR UPDATE OF j` before the path's own `gc_document` update) — a genuine lock-order cycle. Revocation now locates and locks the affected `gc_document_job` rows first, then updates `gc_document`, matching every worker path; `lockDocument`'s KDoc now states the real lock order of every path (confirm/exclude/correct/document-request vs. revocation/worker) and why they cannot cycle. A two-thread integration test races `markExtractionCompleted` against `revokeConsent` on the same document against the real embedded PostgreSQL: it always ends with the document `TERMINATED_BY_REVOCATION` (never `COMPLETED` with candidates still readable), and never with a Postgres deadlock/lock-abort exception on either side. **(Review Fix F6)** Revocation nulls `gc_document.preview_object_key` but deliberately keeps the `gc_preview_artifact` row when the file delete itself fails; `listObjectKeys` (used by `deleteProfile`) previously read only `gc_document`'s own three key columns, so a profile deletion after a failed revocation preview delete could never find and remove that orphaned file. `listObjectKeys` now also left-joins `gc_preview_artifact.object_key`, proven by a test that fails the revocation preview delete and then deletes the profile. **(Review Fix F7)** `revokeConsent` and `deleteProfile` both guard their after-commit file-deletion `registerSynchronization` call with `TransactionSynchronizationManager.isSynchronizationActive()`; called with no active transaction synchronization (proven by a test that constructs the service directly, bypassing the `@Transactional` Spring proxy), each now deletes the files immediately instead of throwing `IllegalStateException`. **(Review Fix F8)** `ExtractedCandidate.originalLabel` now carries `@Size(min = 1, max = 80)` (was `max = 80` only): a blank (but non-null) `originalLabel` is rejected here as `400`, not left to reach the V11 `CHECK (original_label IS NULL OR char_length(...) BETWEEN 1 AND 80)` constraint as a raw, unmapped SQL failure.
- **Benchmark — hand-labelled fixtures (§9).** Three layout-faithful synthetic fixtures generated in code under `packages/korean-checkup-benchmark` (never a committed PDF): `synthetic-hand-nhis-notice` (공단 일반검진 결과통보서형, 이전 결과 column, 혈압 split), `synthetic-hand-hospital-four-column` (항목·결과·단위·참고치, page-continued label, qualified value, glued unit), `synthetic-hand-scan-with-invisible-text` (invisible OCR-style text layer; the parser must not trust it). Expectations are hand-typed in `expected.json`, never generator-produced. Scored by the new `handLabelledAccuracy` metric on corpus `synthetic-ko-hand-labelled-4b20bf06922a7e0a`: measured `0.9166666666666666` (candidates 13/14, abstentions 9/10) after **Review Fix F1** completed the nhis-notice gold set's 혈압-previous-column expectations (split into `혈압(수축기)`/`혈압(이완기)`, matching the fixed parser), pinned as `handLabelledFloor` in `apps/web/lib/medical-ai/evaluation.ts` — not presented as 100%. The existing r2 corpus (`synthetic-ko-checkup-r2-50ed23041bb4af1d`, 31 documents) is untouched and still scores `fieldF1`/`referenceRangeAccuracy`/`conceptAccuracy` all 1.
- Two parser gaps recorded rather than hidden: (1) a label that continues across a page break is not joined (`mergeContinuedLabels` only handles a same-page continuation), so the hospital-four-column fixture's page-continued 총빌리루빈 value is not matched; (2) a qualified-value label can absorb trailing text, contributing to the abstention-accuracy shortfall (9/10, not 10/10) on the current fixtures.

### Limits stated, not hidden

- `apps/web/lib/medical-ai/medgemma-experiment.ts` still lists only 4 of the 7 abstention reasons (`unreadable`, `ambiguous_value`, `ambiguous_unit`, `missing_evidence`) — MedGemma prompt/schema alignment with the full closed set is 7b/MedGemma follow-up, not done here.
- `FoundationProblemAdvice` maps `ConstraintViolationException`/`MaxUploadSizeExceededException` to the product error shape; a generic `404` for an unmatched route is not yet covered (7b) — today's only 404 is the controller-level `FoundationNotFoundException` handler.
- A worker that pulls a lease already dead-lettered by the core still gets a plain `403`, not a more specific reason code — pre-existing behavior, unchanged by this wave.
- The two-thread race test (`FoundationLifecyclePostgresIntegrationTest`) runs one throwaway warm-up round before the timed race to prime the JIT/connection pool; the warm-up rows are deleted before the real race runs.
- `request_sha256` hashes the raw request body/operation/resource-id string; the body is not canonicalised (e.g. no key-sorted re-serialization of JSON), so two requests that are semantically identical but byte-different (field order, whitespace) hash differently and are treated as a key/hash mismatch.
- Sessions, the janitor, rate limits and body caps are entirely 7b — none of §5–§8 is touched by this PR.
- An idempotency key that repeats across two *different* operation types (e.g. reused between a confirmation and a correction) is still accepted as long as each operation's own `(subject, operation, key)` tuple is new — the key is not enforced to be globally unique per subject across every operation, only per operation. Not addressed in this wave.
- A blood-pressure row's systolic and diastolic candidates deliberately share one `sourceTextSha256` and one `evidenceBox` (both are computed from the single printed row before the split) — this is by design, not a defect, but it means the two candidates are not independently distinguishable by evidence alone.
- `FoundationLifecyclePostgresIntegrationTest`'s audit-value assertion (that no audit event ever contains a raw health value) only searches for a handful of literal values actually used in that test's own fixtures (e.g. `188`, `190`) — it is vacuous against any value the test never happens to use, not a general proof that audit rows never contain a value. Similarly, the demo-bootstrap capacity check counts `gc_subject` rows including previously *deleted* subjects (deletion never decrements the counter), which is intentional (a deleted subject must not free up anonymous-provisioning budget) but means the counter is not literally "how many demo subjects exist right now." Both are pre-existing, unchanged by this PR; a general audit-content assertion and a documented capacity-counting note are 7b.
- `apps/web/lib/medical-ai/evaluation.ts`'s `handLabelledAccuracy` metric does not penalize a run that abstains *more* than the gold set expects (an extra, unexpected abstention neither counts against `matchedAbstentions` nor is treated as a false positive) — only a missing expected candidate/abstention or a hallucinated candidate lowers the score. Not addressed in this wave.
- Readiness verdict is unchanged: `NO_GO`. No readiness change in 7a.

Ranked. F7b-01..F7b-19 are stated limits of 7b, not regressions. F7b-25 was raised by the first CI run of PR #18 and is a founder-only acceptance, not a limit. 6. **F7b-06 — image deduplication per `COSStream` loosens `IMAGE_COMPLEXITY`.** The same image object referenced many times counts once, so a document can present more decoded pixels than the limit contemplates. Task 26's own limits:

17. **F7b-17 — the audit-leak query excludes six columns by name.** `countRawHealthValuesInAudit` and the integration assertion search the whole `gc_audit_event` row as JSON text minus `audit_sequence`, `event_id`, `resource_id`, `subject_hash`, `actor_session_hash` and `occurred_at`. Those six are counters, server-generated UUIDs, peppered digests and the row's own write instant; all are full of incidental digits, and leaving `occurred_at` in would make the receipt's `2026-` needle match every row and turn `rawHealthValuesPresentInAudit` into a constant `true`. A value that leaked *into* one of those six columns would therefore hide — it would have to take the shape of a UUID or a 64-character hex digest to do so. Every other column, including any column added after this commit, is searched, which is what the previous three-column form could not promise. The assertion carries a positive control (a needle known to be present in `outcome` must match) so an all-zero result cannot pass vacuously.
18. **F7b-18 — the brief's two forbidden lists disagreed** (`"%"` in its interface note, `"mmol/L"` in its step), and the list that shipped in 7b was `listOf("mg/dL", "g/dL", "mmol/L", "2026-")`. This fix wave replaced it with `listOf("mg/dL", "mmol/L", "ng/mL", "%", "2026-")`: `%` and `ng/mL` are units the synthetic corpus actually writes (HbA1c and vitamin D respectively), and `g/dL` was dropped because it is a suffix of `mg/dL` and so could never match a row `mg/dL` did not already catch. The remaining limit is unchanged: these five needles are the shapes this corpus produces, not a general detector for every value a real document could carry.
19. **F7b-19 — other audit assertions elsewhere in the same test file still name individual columns** (for example the reference-range check that concatenates `event_type`, `resource_type`, `purpose_code` and `outcome`). Only the two assertions named by the task were converted.

This fix wave's own findings (raised by the whole-branch review, 2026-09-19):

20. **F7b-20 — Task 14's 413 does not drain or abort the connection.** `RequestBodyLimitFilter` answers `413 payload_too_large` and returns; it never drains the remaining request body and never aborts the socket. A client that is still uploading when the cap trips keeps writing into a connection the server has already answered on, and what happens next — the container draining it, the write blocking, or the connection being reset — is container behaviour this branch does not test. No test in 7b sends a body larger than the cap over a real socket; the filter is exercised through MockMvc, which has no socket at all. **Untested, not proven broken.**
21. **F7b-21 — Task 18's timeout path can add up to 15 s past its own deadline.** `PageRenderSubprocess.render` gives the child a 60 s wall clock, then on timeout spends up to 5 s reaping the killed child and up to 5 s each joining the writer and reader threads: 75 s worst case before the worker posts `preview_generation_failed`. The worker does not heartbeat during a render, and the core's `worker-lease-ttl` is 2 minutes, so the worst case still fits — with 45 s of margin, not the 60 s the render timeout alone suggests. The 15 s tail is not asserted anywhere and the margin is not defended by a test that would fail if either constant moved.
22. **F7b-22 — the `liveLauncherThreads()` assertion is order-coupled.** The launcher threads are named by two constants shared across every `render()` call, so the assertion after the first render in `PageRenderSubprocessTest` can only say that *no* launcher thread is alive right then, not that the render it follows leaked none. Reordering the two renders in that test changes what the first assertion observes, and a thread leaked by an earlier test in the same JVM would be attributed to whichever render happens to precede the check.
23. **F7b-23 — Task 22's ClamAV signature layer ages silently wherever the build is cached.** The worker Dockerfile runs `freshclam` inside a `RUN` layer, so the signature database is frozen at build time. CI's ephemeral runner has no layer cache and rebuilds it every run, but any environment that does cache layers (a developer machine, a buildx cache, a registry-backed cache) will reuse that layer indefinitely with no signal that the signatures are old. The worker's own 7-day `signatures-stale` health check is the only brake, and it fails the image closed *after* the fact rather than refreshing it; nothing in the build itself pins or checks the signature date.
24. **F7b-24 — Task 15's IP bucket locks out everyone behind a shared NAT.** `createSession` calls `rateLimiter.recordFailure(subjectKey, clientIp)` on the unknown-subject path as well as the wrong-credential path, and `SessionRateLimiter` keeps one failure counter per IP alongside the per-subject one. Repeated attempts against subjects that do not exist therefore fill the `i:<ip>` bucket, and every real user sharing that egress address — one office, one carrier NAT, one corporate proxy — is locked out with them. Counting unknown subjects is what keeps the endpoint from being an enumeration oracle (the whole point of Task 15's silent refusal), so the two properties are in tension; no test covers the shared-address case either way.
25. **F7b-25 — the web runtime image carries four unfixed Critical CVEs, accepted in-repo and pending a founder decision.** The blocking Trivy step on PR #18's first run ([https://github.com/ji-hun-git/dna/actions/runs/35392935950](https://github.com/ji-hun-git/dna/actions/runs/35392935950)) failed `runtime image (web)` with four Criticals in the Debian 12 base that have no fixed version and so cannot be cleared by the runtime stage's `apt-get upgrade`: `perl-base` CVE-2026-13221 (Trivy status `affected`), CVE-2026-42496 (`fix_deferred`), CVE-2026-8376 (`affected`, reported against 32-bit builds), and `zlib1g` CVE-2023-45853 (`will_not_fix`, in minizip's `zipOpenNewFileInZip4_6`). The documented acceptance route was taken rather than weakening the gate: the four ids are listed in `apps/web/.trivyignore`, each with its package, Trivy status, a one-line reachability argument (the runtime stage's only process is `node apps/web/server.js`; no perl is ever invoked, and Node's zlib bindings do not use minizip) and `# review-by: 2026-10-18`. The file is wired only into the web matrix entry's blocking step (`trivyignores: ${{ matrix.trivyignore }}`, empty for core-api and document-worker); `ignore-unfixed` stays `false` for all three images. **The reachability argument is reviewed, not proven by a run**, and the acceptance is a founder-only decision: it stands until the founder confirms it or a base-image change retires it, and no later than the 30-day review date.

- **Renderer Errors are no longer swallowed.** `DocumentWorkerMain`'s `runCatching { PageRenderSubprocess.render(source) }` caught `Throwable`, so an `OutOfMemoryError` or `StackOverflowError` in the worker's *own* JVM became a retryable `preview_generation_failed` and never reached the loop's deliberately `Exception`-only catch and its fatal halt. It now rethrows any `Error`; an `InterruptedException` re-sets the interrupt flag `runCatching` swallowed before returning the retryable outcome. The two `runCatching` blocks around the launcher's stdin/stdout threads in `PageRenderSubprocess` got the same treatment one level down — an `Error` there would have ended the thread quietly and published a short buffer, so `render()` would have returned a truncated-but-plausible PNG. Both threads now record the first `Error` in an `AtomicReference` and `render()` rethrows it after the join, on the timeout path as well as the normal one. `IOException` stays swallowed: a broken pipe is the normal end of a killed child.
- **No test covers the `Error` rethrow, and the reason is structural.** `PageRenderSubprocess`'s only seam is `entryPoint`, which chooses the *child*'s main class. The `Error` this change is about is raised in the *parent*'s reader thread, which the child cannot reach — the capture is bounded at `MAX_PNG_BYTES + 1` (2 MiB), so no child output can provoke an `OutOfMemoryError` there either. `DocumentWorkerMain` has no seam for the renderer at all (`PageRenderSubprocess` is an object referenced directly). Injecting one would have meant adding a production parameter that exists only for the test, so the change was kept minimal and this limit is stated instead of hidden. **The rethrow is reviewed, not proven by a run.**
- **Audit needles are escaped as literals.** `countRawHealthValuesInAudit` built its POSIX alternation with `Regex.escape(...)` and then stripped the `\Q...\E` markers PostgreSQL does not implement, escaping only `.`. Every other metacharacter stayed live: `HbA1c (%)` compiled to a group and matched the different text `HbA1c %`, and an unbalanced `(` made the query throw rather than find nothing. `FoundationRepository.escapePosixRegexLiteral` now escapes the full set `[ ] ( ) { } . * + ? ^ $ | \`, and the integration test's `auditRowsContaining` helper uses the same function so the two cannot drift. A new PostgreSQL test, `audit leak needles are matched as literal text and never as regular expression syntax`, inserts one audit row containing `PROBE_HbA1c (%)` and pins four cases: the parenthesised literal matches, the group-expansion `PROBE_HbA1c %` does not, a trailing `(` finds the row instead of throwing, and a needle containing `|` is one literal rather than two alternatives. It fails on the old escape (verified: `AssertionFailedError` at the first assertion) and passes on the new one.
