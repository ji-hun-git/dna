## What exists now
- **Series API.** `GET /api/foundation/series` (owner-isolated, `Cache-Control: no-store`, CURRENT records only): one series per concept (same `concept_code`, else same label — connected components, because that rule is not transitive) and unit, points ordered by exam date (then confirmation instant, then record id). `derived` is always present and carries up to three numbers, always computed in time order: `lastDifference` (the Wave 3 calculator and its narrowed rules — percent only when the previous value is positive and the unit is not `%`), `per30Days` (HALF_EVEN, one more decimal than the inputs, omitted when the two dates are equal), `meanOfLast3` (HALF_EVEN, one more decimal, omitted under three numeric values); each key is simply omitted, never null, when not computable. No reference-range key or text, and no audit row is written for this read, consistent with the sibling reads.
- **측정 이력 (`/my-data/history`).** Not built. See "Scope note" above. `getSeries()` (`apps/web/lib/foundation/client.ts`) is a strict zod client for `/api/foundation/series` but is not yet called from any screen.

## 최종 리뷰 후 좁힌 점
- **F1.** `per30Days` is now also omitted when the gap between the last two points is under 30 days, so the figure is never an extrapolation from a one- or two-day gap.
- **F2.** `lastDifference` is now omitted when the last two points share the same `observedOn`, since which one is "last" would otherwise depend on confirmation click order.
- **F3.** FHIR `category` is now omitted (never `vital-signs`) for the catalogue's vital-sign concepts (blood pressure, pulse, height, weight, BMI, waist circumference) and for events with no concept code; `laboratory` is kept only for concepts that are genuinely laboratory results.
- **F4.** The FHIR mapper now emits no `code.coding` for the four concepts whose alias dictionary merges a loose label onto a specific LOINC code (`fasting-glucose`, `crp`, `total-bilirubin`, `egfr`); `code.text` still carries the original label.
- **F5.** Every FHIR `Observation` now carries its own `meta.tag` (`synthetic` and `person-confirmed-from-document`), so the provenance survives extraction of a single Observation out of the Bundle.

## Limits
No hosted run. The three numbers are arithmetic on values the person confirmed; they carry no meaning. The 측정 이력 screen that would show the graph and the numbers together is not built — it is parked at the founder's request ("나중에 볼게요, 백엔드 먼저") pending review of the published mockup, so nothing on this branch yet displays a band, threshold, fitted line, forecast or direction language; adding the screen still needs no new intended-use decision (it is already covered by `governance/intended-use-decision-measurement-history-2026-09-17.md`) but does need a regulatory review before real personal health information is processed, exactly as that decision states. The FHIR file is a hand-written subset (no `Patient` resource, no UCUM coding, no `fullUrl`, not validated against any profile — no FHIR validator was run, only structural tests). FHIR import is out of scope. Known limits carried from review: a bare number printed before a range drops the range; a row with spaces inside two ranges abstains rather than being captured; `ratio(0,0) = 1` prints as 100% for a run with no matched measurements; owner isolation for the new reads is asserted with the same empty-result pattern used by the sibling reads, not a dedicated negative-authorization test; `lastDifference.percent`'s web-side schema also tolerates null. The founder's no-regulatory-review judgement (`governance/intended-use-decision-measurement-history-2026-09-17.md`) applies to synthetic staging only and must be revisited, with a regulatory review, before any real PHI is processed. Readiness is unchanged.

Additional limits found in the final whole-branch review: alias merging means a loosely labelled row (for example a non-fasting "혈당") shares a series and a three-value mean with the specific concept it is aliased to ("공복혈당"/fasting glucose); narrowing the aliases so a non-fasting reading gets its own concept is a follow-up, not done here. A series longer than 500 points is rejected whole by the web schema, while the server itself has no such cap. A non-numeric value exported as `valueString` carries no unit — the unit is only ever attached to `valueQuantity`. Commit `100044f`'s subject line mentions measurement-history and 320px work that the commit does not actually contain (its content is e2e coverage only); the subject was not corrected because it is already pushed history.
