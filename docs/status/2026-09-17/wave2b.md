# Wave 2B evidence — MedGemma 1.5 local synthetic experiment, labelled exam dates, date correction, benchmark determinism (2026-09-17)

Branch `codex/wave5-medgemma-eval-and-dates`. Synthetic only. Release remains NO_GO; no readiness gate or verdict changed. PR deferred.

## What exists now
- **Worker date rule.** Only a labelled date (검사일/검진일/채취일/검사 일자/검진 일자/채취 일자/Date/Exam date/Test date/Collection date, label anywhere in the line, first date after the label) is the document date. A bare date is never used. English "Date of birth"/"Birth date" is explicitly excluded from the label match (lookahead/lookbehind guards), so a birth date next to a real exam date is never mistaken for one. Two different labelled dates make the whole document one `ambiguous_value` abstention (`문서 전체`) with zero candidates; the review screen names it "검사일이 둘 이상이라 확실하지 않음". No labelled date → every recognised row is `missing_evidence` (unchanged). The two demo PDFs carry `Date:` and parse as before.
- **Date correction.** `POST /api/foundation/candidates/{id}/confirmation` accepts an optional `observedOn` (ISO date, 1900-01-01..today Asia/Seoul; 400 `observed_on_invalid` / `observed_on_out_of_range`). V8 adds `gc_health_record.original_observed_on`; the candidate row keeps its own date. `RecordReceipt.originalObservedOn` is always present; `reviewDecision = CORRECTED` when the value or the date differs; `HealthEvent.corrected` follows. Audit stays `CANDIDATE_CONFIRMED`/`CANDIDATE_CORRECTED` with no date and no value. The review card has a "검사일 수정" form (`type=date`, future and pre-1900 refused); the records screen shows "사용자가 검사일을 수정함 · 원래 YYYY. M. D.". This is a confirmation of what the document says, not clinical validation.
- **Benchmark R2.** 25 documents (4 layouts × 6 variants + `synthetic-hospital-two-column-v6`, which prints 생년월일 before a mid-line labelled 검사일). PDF bytes are deterministic (fixed PDFBox document id and info dates, no XMP; proven by a two-generation byte test). `corpusId = synthetic-ko-checkup-r2-<first 16 hex of sha256 over "<documentId> <sha256(pdf)>" lines>`. New CLIs `render-pages` (PDFBox 150 dpi PNG per page, 31 pages) and `export-concepts`.
- **MedGemma experiment.** `pnpm medical-ai:medgemma-experiment` (manual, not in CI) renders the corpus, sends each page to the local Ollama `medgemma1.5:latest` with a pinned transcription-only prompt, JSON-schema `format`, `think:false`, temperature 0, `num_predict:4096`, one call per page, 180 s per document, maps rows to `medical-document-run.v1` with the whole-page box and catalogue aliases, drops any `referenceRange`, strips reference-range fragments out of the transcribed `unit`, scores parser and model with the same `evaluateMedicalDocumentPipeline`, and writes `docs/status/2026-09-17/medgemma-local-experiment.md`. A runner failure (timeout/HTTP error/malformed JSON) scores under its own `fieldId: "runner-failure"`, never the gold document-level `fieldId: "document"`; a blank model label gets its own `unknown-<index>` identity instead of folding into the document label. A JSON parse failure captures Ollama's `done_reason`/`eval_count` and the raw content, persisted under `apps/web/build/medgemma/raw/<documentId>-failed.json`. Run JSON stays under `apps/web/build/medgemma/`. Model output never enters product code.

## Limits
No hosted run. One local execution of one quantized model on 31 synthetic pages; no real layout, scan or PHI was measured. The result measures "MedGemma 1.5 under this fixed protocol (prompt, schema, options)", not the model's performance in general. Evidence localization for the model is not measurable. The previous run's 8 unreadable documents were consistent with the 2048-token `num_predict` cap in timing, not proven to be caused by it; this run raised `num_predict` to 4096 and still saw 9 documents fail with `done_reason=length` (observed `eval_count` mostly ~3494, short of the 4096 cap), so the image-token-inclusive context budget may be the real bottleneck rather than `num_predict` alone. The required-abstention-recall metric never credits a runner failure (timeout, HTTP error, malformed JSON) as a correctly-recognised gold abstention — a failed call is scored under its own `fieldId: "runner-failure"`, which cannot match the gold document-level `fieldId: "document"`. The corpus's printed reference-range text can leak into the model's transcribed `unit` field (e.g. "U/L (15-35)"); that range text is stripped before scoring. Handoff conditions 2–7 in `docs/implementation/medical-document-runner.md` remain open. Nothing here is a diagnosis, normality, reference-range, trend or risk claim.
