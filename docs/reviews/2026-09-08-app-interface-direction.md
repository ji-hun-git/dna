# 앎: 웹사이트보다 앱이 맞을까?

검토일: 2026-09-08. 상태: **제품 방향 제안**, 플랫폼 전환 승인이나 출시 증거가 아닙니다.
검토 코드 기준: `dc417df3adac1569008f33e1056ff4aea22fc6df` 및 이번 기록 재조회 수정.

## 결론

**앱 중심의 사용 경험은 맞습니다. 지금 네이티브 앱으로 다시 만드는 것은 권하지 않습니다.**

앎의 핵심은 소개 페이지를 읽는 일이 아니라, 결과지를 확인하고 기록을 쌓아 다음 진료에
다시 사용하는 일입니다. 따라서 일상적인 제품 화면은 모바일 앱처럼 설계하고, 먼저
현재 웹 기술로 완성하는 편이 낫다는 판단입니다. 이것은 사용자 행동이 입증된 결론이
아니라 현재 코드와 제품 목적에 근거한 제안입니다.

추천 구성은 다음과 같습니다.

- **서비스 본체:** 모바일 우선 웹앱. 홈 / 기록 / 진료 준비 / 데이터의 현재 틀 유지.
- **큰 화면:** 같은 서비스에서 원문 대조, 여러 날짜 비교, 질문 인쇄를 지원.
- **소개 웹사이트:** 서비스 설명과 신뢰·이용 안내를 담당. 제품 본체와 역할만 구분하며,
  이번 작업에서 별도 도메인이나 인증 경계를 만들지 않습니다.
- **설치형 웹앱:** 복구 가능한 계정과 배포 경계가 검증된 뒤 선택적으로 제공.
- **iOS/Android 앱:** 촬영·파일 공유·기기 연동 등 실제로 필요한 기능이 검증되면 추가.

## '앱 인터페이스'와 '앱 설치 파일'은 다른 결정

| 선택 | 앎에서의 가치 | 비용·제약 | 지금 판단 |
|---|---|---|---|
| 앱처럼 설계한 반응형 웹 | 설치 없이 체험, 네 개의 작업 중심 화면, PC 원문 검토도 유지 | 기기 통합과 설치 경험에 한계; 실제 모바일 브라우저 검증 필요 | 지금 집중 |
| 설치 가능한 웹앱(PWA) | 홈 화면 아이콘과 독립 실행 창, 기존 웹 코드 재사용 | 설치 방법·지원이 브라우저마다 다름; 설치가 계정 복구나 오프라인 보관을 만들지는 않음 | 다음 검증 후보 |
| 네이티브 기능을 가진 모바일 앱 | 문서 촬영, OS 파일 공유 수신, 필요한 기기 API 활용 | 기기별 권한·보관·복구·배포·테스트가 추가됨; 현재 백엔드 미완성 문제는 그대로 | 요구 검증 후 |

설치형 웹앱은 별도 앱 같은 창에서 실행할 수 있고, 설치 가능 여부와 오프라인 기능은
동일한 조건이 아닙니다. 플랫폼별 설치 흐름도 다릅니다.
[MDN 설치 가능성 안내](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

## 현재 저장소에서 확인한 것

- `IntegratedShell.tsx`: 네 개의 제품 경로와 현재 메뉴 표시가 이미 있습니다.
- `globals.css`: 모바일 고정 하단 메뉴와 safe-area 여백이 이미 있습니다. 이것만으로
  실제 iPhone/Android 키보드·노치·확대 접근성이 검증됐다고 말할 수는 없습니다.
- 주요 화면은 Next가 보여 주고, Spring이 세션·동의·원문·검토·기록의 권한을 관리합니다.
  기존 백엔드를 버릴 이유가 없습니다.
- 이번 조회에서 추적 파일 목록에 `pubspec.yaml`, `AndroidManifest.xml`, `Info.plist`,
  `manifest.webmanifest`가 발견되지 않았습니다. 계획에 앱이 등장하는 것과 실행 가능한
  앱이 존재하는 것은 다릅니다. 이번 작업에서 앱 설치 파일이나 PWA를 만들지 않았습니다.
- 현재 체험 계정은 세션 만료나 쿠키 손실 후 복구할 수 없습니다. 앱 아이콘을 붙여도
  이 문제는 해결되지 않으므로, 장기간 내 기록을 보관한다는 약속이 먼저 나가면 안 됩니다.
- 원문 후보는 고정 합성 예시입니다. 촬영 화면을 추가한다고 실제 OCR이 되는 것도 아닙니다.

## 네이티브 앱을 만들 이유가 생기는 시점

1. **촬영이 반복적으로 막힐 때:** 여러 페이지 촬영·잘라내기·재촬영이 핵심 요구인지
   관찰합니다. Apple은 페이지별 문서 스캔용 VisionKit 인터페이스를 제공합니다.
   스캔은 텍스트 추출 정확도나 임상 검증을 의미하지 않습니다.
   [Apple 문서 카메라](https://developer.apple.com/documentation/visionkit/vndocumentcameraviewcontroller).
2. **OS 건강 데이터가 실제 제품 가치에 필요할 때:** HealthKit/Health Connect는 각각
   기기 플랫폼의 권한·지원 조건을 검토해야 합니다. 이는 현재 앎에 구현된 연결이 아닙니다.
   [Apple HealthKit](https://developer.apple.com/documentation/healthkit),
   [Android Health Connect](https://developer.android.com/health-and-fitness/health-connect/get-started).
3. **오프라인 조회가 필수일 때:** 암호화·잠금·키 분실·기기 이전·백업·삭제를 함께 설계해야
   합니다. 건강 API 응답을 브라우저 캐시에 넣는 것만으로 해결하지 않습니다.
4. **앱 설치가 재방문에 도움이 된다는 관찰이 있을 때:** 설치 수나 인터뷰 호감이 아니라,
   다음 문서를 추가하고 원문·질문을 다시 찾는 행동으로 판단합니다.

현재 단계에서는 푸시 알림이나 건강 데이터 연결을 추가해 재방문을 만들어 내지 않습니다.
플랫폼 건강 데이터 권한, 사회적 로그인, MyHealthWay 동의는 서로 대체되지 않습니다.

## 개발 순서 제안

### 지금: 웹 기술로 앱 경험을 완성

현재 프레임과 글꼴을 유지합니다. 한 화면에서 할 일을 분명히 하고, 원문이 보이지 않을
때 확인을 막으며, 뒤로 가기·다시 열기·통신 실패 후 재시도를 일관되게 만듭니다.
이번에는 기록 읽기 실패와 로그인 만료를 구분해, 통신 장애 때문에 체험 계정을 새로
만들도록 유도하지 않게 수정합니다. 기록 수정 요청은 자동 재전송하지 않습니다.

### 다음: 서비스의 지속성과 운영 검증

PR 독립 리뷰, 저장소·큐, 비공개 합성 스테이징과 복구 검증을 기존 계획대로 진행합니다.
장기 사용을 말하기 전에 복구 가능한 사용자 계정 설계가 필요합니다. 이것은 N1 저장소
인터페이스 작업과도 별개의 계약이며, 앱 선택을 이유로 인증 범위를 확장하지 않습니다.

### 그다음: 선택적 설치 실험

합성 데이터·검증된 호스팅 범위에서 manifest/아이콘/standalone 실행을 검토합니다.
첫 실험에서는 개인 기록·원문·API 응답을 service worker, IndexedDB, localStorage에
새로 저장하지 않는 제안을 우선 검토합니다. 설치 후 로그인, 세션 만료, 재시작,
브라우저와 설치 창 사이의 상태 차이, 삭제 후 잔존 데이터를 실제 기기로 시험합니다.
설치를 강제하지 않고 일반 브라우저 경로도 유지합니다. 이번 변경에는 포함하지 않습니다.

### 조건 충족 시: 모바일 전용 기능

기존 `governance/decision-log.md` D-022는 **오프라인 Flutter 보관함**을 계획하며,
서버 계정·네트워크·백그라운드 동기화를 허용한 결정이 아닙니다. 연결형 모바일 앱을
만들려면 그 차이를 명시한 별도 설계 검토가 필요합니다. Flutter/React Native/네이티브
중 하나를 지금 확정하거나, 단순 WebView 포장이 동일한 보안 경계를 준다고 가정하지 않습니다.

## 전환을 결정할 실험

기존 U1 관찰 계획의 합성 문서 작업을 먼저 실행합니다. 촬영이 필요한 경우에는 새로
생성한 종이 예시만 사용하고 실제 결과지를 받지 않습니다. 참여·기록 동의는 별도로 정합니다.

측정할 것은 완료율, 도움 요청, 첫 확인까지 걸린 시간, 원문을 다시 찾는 성공 여부,
앱이 건강 상태를 판단한다고 오해한 횟수입니다. 설치 실험에서는 재시작 후 다시 진입할
수 있는지와 같은 작업을 더 쉽게 끝내는지를 비교합니다. 기기별 장애가 반복되고 네이티브
시제품이 해당 장애를 줄인다는 증거가 있을 때 범위를 확대합니다. 수치나 결과를 미리
성공으로 기록하지 않습니다.

## 유지되는 경계

이 문서는 앱 전환·배포·외부 계정·건강 데이터 연결을 승인하지 않습니다. 앎은 출처를
확인한 기록 서비스이며 진단 앱이 아닙니다. 연구용 DataON/AIDA 런타임과 개인 기록
런타임은 계속 분리합니다. 실제 데이터와 의료 AI는 비활성 상태이고 출시 판단은 NO_GO입니다.
